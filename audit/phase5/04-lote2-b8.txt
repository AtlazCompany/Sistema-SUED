FASE 5 / LOTE 2 — IMPLEMENTAÇÃO DO ACHADO B8 (CRUD DE CONTACT)
==================================================================

--------------------------------------------------------------------
INVENTÁRIO (antes de alterar qualquer arquivo)
--------------------------------------------------------------------

Schema (`Contact`, confirmado via `inspect-db.mjs`): só 4 colunas —
`id`, `clientId` (FK NOT NULL → `Client.id`), `name` (NOT NULL),
`primary` (boolean NOT NULL, default `false`). Sem `email`/`phone`/
`notes` próprios — o cadastro de contato aqui é deliberadamente
mínimo (nome + "é o principal?"), o e-mail/telefone de contato geral
já vive no próprio `Client`.

Relação com o resto do sistema: só existe UMA leitura hoje —
`GET /api/clientes/:id` ([server/routes/clientes.js](server/routes/clientes.js),
já existente) devolve `contacts` embutido (`select * from "Contact"
where "clientId" = ... order by "primary" desc, name asc`). Nada mais
no backend nem no frontend lê, cria, edita ou exclui `Contact` — nem
mesmo uma tela que MOSTRE o cliente em detalhe existia
(`public/src/views/clientes.js` era só lista + criar/editar/excluir,
sem drill-down nenhum).

Padrão análogo já existente no mesmo projeto para "marcador único por
grupo" — `SupplierProduct.isDefault` (`server/routes/catalogo.js`):
ao marcar um vínculo fornecedor↔item como padrão, os outros do mesmo
item são desmarcados. Usado aqui como precedente direto para o
significado de `Contact.primary` (no máximo um principal por
cliente) — decisão técnica de consistência, não uma regra de negócio
nova (o nome da coluna já implica isso).

Lacuna exata: nenhuma rota `POST`/`PUT`/`DELETE` para `Contact`;
nenhuma UI para gerenciar contatos.

--------------------------------------------------------------------
PLANO
--------------------------------------------------------------------

Backend, em `server/routes/clientes.js` (mesmo arquivo — `Contact` é
sempre acessado através de um `Client`, mesmo padrão de
`catalogo.js` gerenciar `SupplierProduct` no seu próprio arquivo):
  - `POST /api/clientes/:clientId/contatos`
  - `PUT /api/clientes/contatos/:id`
  - `DELETE /api/clientes/contatos/:id`
  - Mesmo módulo RBAC já usado por Cliente (`crm`) — nenhuma
    permissão nova precisou ser criada.
  - Mesmo tratamento de FK do achado B1 (23503 → 400 amigável) na
    criação, para `clientId` inexistente.

Frontend, em `public/src/views/clientes.js`: em vez de uma tela de
detalhe nova (seria redesign, fora do pedido de "CRUD mínimo"), um
botão "Contatos" por linha da lista abre um modal — mesmo padrão já
usado em `categoriesModal()` (`public/src/views/catalogo.js`): lista +
adicionar inline + excluir, aqui com um botão extra "Tornar
principal" por contato não-principal.
