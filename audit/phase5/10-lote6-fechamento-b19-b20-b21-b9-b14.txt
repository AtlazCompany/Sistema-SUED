9. PROBLEMA ADICIONAL ENCONTRADO E CORRIGIDO — REGRESSÃO REAL
--------------------------------------------------------------------

**Não foi instabilidade de infraestrutura/Supabase.** Diagnóstico:

`"AuditLog"."userId" REFERENCES "User"("id")` foi criada, na
implementação original do B9, com o padrão `RESTRICT` do Postgres em
vez de `ON DELETE SET NULL` — uma contradição direta com o próprio
design já aprovado do B9 (a proposta original dizia explicitamente que
`userName` fica congelado "para o log continuar legível MESMO QUE O
USUÁRIO SEJA EXCLUÍDO DEPOIS"). Isso não é uma decisão nova de
arquitetura — é a implementação não tendo seguido o design já
combinado.

**Efeito observado**: qualquer usuário de teste que executasse UMA
ação de escrita em Financeiro/Contratos/Usuários (o escopo do B9)
passava a ter uma linha em `"AuditLog"` como ator (`userId`). Quando um
teste pré-existente (de ANTES do B9 existir — `usuarios.test.js`,
`fk-write-guards.test.js`) tentava apagar esse usuário via SQL direto
(bypassando a rota da API), o Postgres recusava com `23503` — erro não
tratado nesses testes antigos, que não previam essa FK nova.

**Confirmado real, não intermitente**: reproduzido de forma
determinística ao rodar `usuarios.test.js` isoladamente 2 vezes
seguidas, mesma falha nos dois casos, com stack trace do Postgres
apontando exatamente para a constraint `AuditLog_userId_fkey`.

**Correção**: `ALTER TABLE "AuditLog" DROP CONSTRAINT
"AuditLog_userId_fkey"` + `ADD CONSTRAINT ... FOREIGN KEY ("userId")
REFERENCES "User"("id") ON DELETE SET NULL`. Por exigir `ALTER TABLE`,
a alteração foi apresentada e autorizada explicitamente pelo usuário
antes de ser executada — como o classificador de segurança do
ambiente bloqueou a execução automatizada mesmo depois de uma regra de
permissão ter sido adicionada, o próprio usuário rodou o comando
manualmente pelo painel SQL do Supabase. Confirmado depois via
`pg_constraint` (`confdeltype = 'n'` = SET NULL). `server/
setup-audit-log.mjs` também corrigido, para que uma instalação nova já
saia com a constraint certa desde o início.

**Reconfirmação**: `usuarios.test.js` + `fk-write-guards.test.js`
reexecutados isoladamente após a correção — 67/67 PASS. Suíte completa
reexecutada do zero — 255/255 PASS.

Durante o diagnóstico, também foram encontrados e removidos 12
usuários de teste órfãos (`audit.fase2.*`/`audit.fase5.*`) e 3
registros órfãos (`Client`/`ProductService`/`Category`) deixados por
execuções anteriores desta mesma janela que precisaram ser
interrompidas à força (processo travado, não relacionado ao código —
ver observação abaixo) — não fazem parte da regressão em si, mas
precisavam ser limpos antes de a suíte rodar de forma confiável.

**Observação de ambiente (não é bug de código)**: uma execução da
suíte completa travou de verdade (processo vivo, sem produzir mais
saída por >5 minutos, mesmo sendo o último arquivo da fila) — não uma
falha de teste, um travamento real do processo Node, encerrado
manualmente. Causa provável: conexões de banco não liberadas
corretamente quando um `after()` de teste lança um erro (como
aconteceu ali, pela regressão descrita acima). Não gerou nenhuma
alteração de código — resolvido corrigindo a causa raiz (a
constraint), que eliminou o erro que provocava a trava.
