--------------------------------------------------------------------
DIAGNÓSTICO (resumo — análise completa apresentada e aprovada antes da
implementação, reproduzida aqui por completude do relatório)
--------------------------------------------------------------------

Trocar a senha (própria, via `PUT /api/auth/senha`, ou administrativa,
via `POST /api/usuarios/:id/redefinir-senha`) reemitia cookie só para
a sessão que fez a ação — sessões antigas (outro dispositivo/aba, ou a
sessão que a pessoa já tinha aberta quando um admin redefine a senha
dela) continuavam válidas até o JWT expirar sozinho (até 8h). Já
documentado desde a Fase 2, avaliado e não implementado nas Fases 2 e
3 por exigir alteração de schema sem aprovação explícita.

--------------------------------------------------------------------
ALTERAÇÃO DE SCHEMA (a única desta fase, autorizada explicitamente)
--------------------------------------------------------------------

`server/setup-token-version.mjs` — script único e idempotente (mesmo
padrão de `server/setup-numbering.mjs`, já usado desde a Fase 1):
  `ALTER TABLE "User" ADD COLUMN "tokenVersion" integer NOT NULL DEFAULT 0`

Executado contra o Supabase real em 2026-08-26. Confirmado antes e
depois: nenhuma linha existente foi alterada além do preenchimento
automático do valor padrão (`0`) pelo próprio Postgres — o único
usuário real (`contato.atlazcompany@gmail.com`) recebeu
`tokenVersion = 0`, sem qualquer outro campo tocado.

--------------------------------------------------------------------
IMPLEMENTAÇÃO
--------------------------------------------------------------------

`server/auth.js`:
  - `sign(user)` — payload do JWT ganhou `tokenVersion: user.tokenVersion ?? 0`.
  - SELECT do login — passou a trazer `"tokenVersion"` também.
  - `resolveSession()` — passou a comparar `(payload.tokenVersion ?? 0)`
    contra `(user.tokenVersion ?? 0)` do banco; divergência → nova razão
    `stale_token`, mensagem "Sua senha foi alterada. Faça login
    novamente." (mesmo mecanismo de `SESSION_ERROR_MESSAGES` já usado
    para `inactive`/`not_found`).
  - `PUT /senha` — o UPDATE que grava o novo hash agora incrementa
    `"tokenVersion" = "tokenVersion" + 1` na MESMA instrução; o cookie
    reemitido para a aba atual já usa a nova versão (só essa sessão
    continua sem precisar logar de novo).

`server/routes/usuarios.js`:
  - `POST /:id/redefinir-senha` — mesmo incremento de `tokenVersion` no
    UPDATE, para que uma redefinição administrativa também derrube
    qualquer sessão que a pessoa já tivesse aberta (o caso mais
    importante do achado: normalmente é usado por suspeita de conta
    comprometida).

Uso de `?? 0` dos dois lados da comparação: garante que tokens já
emitidos ANTES desta mudança (sem a claim `tokenVersion`) continuem
válidos contra a coluna nova (que também começa em `0`) — ninguém foi
deslogado à força pelo deploy desta correção.

Nenhuma rota individual das 13 protegidas por `requireAuth` foi
tocada — o efeito se propaga automaticamente pelo mesmo mecanismo
central já usado desde a correção de sessão da Fase 2.

--------------------------------------------------------------------
BUG ENCONTRADO E CORRIGIDO DURANTE OS TESTES (não era conhecido antes)
--------------------------------------------------------------------

`server/tests/password-change-rate-limit.test.js` (Lote 1, banco
mockado) quebrou ao rodar a suíte completa: seu dublê de `sql`
assumia que o PRIMEIRO valor interpolado numa query era sempre a
chave de busca do usuário (email no login, id no restante). O novo
UPDATE de troca de senha interpola o HASH da nova senha antes do id
na cláusula WHERE — o dublê pegava o hash como "chave", não achava
usuário nenhum, e a query de `UPDATE ... RETURNING "tokenVersion"`
devolvia um array vazio, que o código tentava desestruturar
(`const [{ tokenVersion }] = ...`) e estourava um erro de runtime
(500). Corrigido SÓ no dublê de teste (não é um bug de produção): a
busca agora procura, entre TODOS os valores interpolados, um que bata
com um usuário conhecido, em vez de assumir a posição.
