--------------------------------------------------------------------
IMPLEMENTAÇÃO
--------------------------------------------------------------------

B1 — em cada uma das 15 rotas listadas acima, o INSERT/UPDATE passou a
ser protegido por `try/catch`, mapeando `e.code === "23503"` para
`HttpError(400, <mensagem amigável específica da rota>)` — mesmo
padrão exato já usado e validado nas rotas `DELETE` desde a Fase 4,
adaptado para o código HTTP correto do cenário (400 = "a referência
que você mandou não existe", diferente do 409 usado no DELETE = "não
posso apagar porque outros registros dependem disto"). Onde já
existia um `catch` (ex.: `eventos.js` e `catalogo.js`, que já tratavam
`23505` para duplicidade), o `23503` foi adicionado como um branch a
mais no mesmo bloco, sem duplicar `try/catch`.

Em `orcamentos.js`, o `POST`/`PUT` usam uma transação
(`sql.begin(async (tx) => {...})`) — o `try/catch` envolve a chamada
inteira a `sql.begin(...)`: se qualquer INSERT/UPDATE dentro da
transação falhar com 23503, a biblioteca `postgres` já garante o
ROLLBACK antes de relançar o erro, então um único `catch` externo é
suficiente (confirmado por teste real: nenhuma linha órfã fica no
banco quando um item de orçamento referencia um `productServiceId`
inexistente).

Nenhuma regra de negócio foi alterada além do tratamento técnico do
erro — nenhum campo passou a ser obrigatório/opcional diferente do que
já era, nenhuma validação de conteúdo foi adicionada (só "essa
referência existe no banco?", que é exatamente o que a FK do Postgres
já impunha — antes só vazava feio, agora vaza com uma mensagem
decente).

B6 — `server/auth.js`: novo rate limit em memória para
`PUT /api/auth/senha`, no mesmo padrão do `loginRateLimit` existente
(mesma janela: 10 minutos; mesmo limite: 8 tentativas; mesmo cabeçalho
`Retry-After`; mesmo código de status 429). Diferença deliberada:
chaveado por `req.user.id` (não por IP) — a rota já exige sessão
autenticada (`requireAuth` roda antes), então a chave correta pra
isolar o "abuso" é a CONTA sob ataque, não o IP de quem está batendo
(evita punir outras pessoas atrás do mesmo IP/proxy corporativo por
causa de uma única conta comprometida). Só tentativas com a senha
ATUAL errada contam para o limite — erros de validação (senha nova
curta, confirmação ausente ou diferente) não consomem a cota, porque
não são tentativas de adivinhação de senha. Nenhuma dependência nova
(`Map` em memória, mesma técnica já usada no login).

--------------------------------------------------------------------
AMBIGUIDADES ENCONTRADAS
--------------------------------------------------------------------

Nenhuma exigiu parar e perguntar. As únicas decisões tomadas durante a
implementação foram técnicas, dentro do escopo já autorizado:
  - Código HTTP 400 (não 404) para toda referência inválida em
    POST/PUT, reservando 409 só para o padrão já existente de DELETE
    bloqueado por FK — escolha de consistência de API, não de regra de
    negócio.
  - Mensagens de erro nomeiam os campos possíveis em linguagem
    simples, sem tentar identificar qual EXATAMENTE falhou (evitado
    de propósito: inspecionar `constraint_name` do erro do Postgres
    acoplaria o código a nomes internos de constraint, mais frágil
    para o mesmo benefício).
  - B6 chaveado por usuário (não por IP), pela razão técnica já
    explicada — não é uma mudança de política de segurança além do
    que foi pedido ("mesmo padrão de segurança já utilizado no
    login", adaptado ao fato de que aqui já existe usuário
    autenticado).
